# Native Agents and Capabilities

`NativeAgentsWorkspace` and `NativeAutomationWorkspace` bind the existing domain panels to the current canonical user, tenant, request actor, role, API instance, API origin, biometric access and foreground lifetime. A private navigator removes open inspectors and dialogs with the same scope. The shared authorized transport verifies the selected credential through bootstrap before dispatch; the local lifetime remains part of that binding during admission and retry.

The existing published operations remain authoritative: Agent create/update, exact task cancellation, release/adaptation actions, Moltbook controls, plugin preview/install/enable/disable/uninstall. Skill writes, Agent deletion, OAuth setup and unsupported workflow editing remain browser handoffs. The mobile Capabilities view now inspects skills, installed connections, custom connections and tools, and exposes the existing plugin preview/lifecycle workflow. macOS retains its six existing sections.

Reads use fresh authorized transport and reject an inventory above 1,000 top-level entries or a response above 4 MiB instead of silently truncating it. Independent source failures remain unavailable. UI detail displays disclose their own smaller text limit. Retrieved URLs and metadata are displayed as data; browser handoff uses the fixed first-party helper.

Before an enrolled write, an AES-GCM encrypted device journal saves only method, operation, exact resource path, request key, request digest, time and reconciliation state. It never persists request bodies, credentials or an executable queue. Its stable owner is API origin, tenant and canonical user; email and role changes cannot hide an earlier unknown outcome. Current request authority remains separate. The specialist namespace is bounded to 32 records / 1 MiB by the shared broker. Unknown outcomes survive navigation and application restart. A plugin installation shares one uncertainty boundary across enable/disable/uninstall; Agent definition and governance writes share the exact Agent boundary. Reload protected recovery performs only a fresh encrypted broker read after storage/CAS uncertainty.

No request automatically replays. A fresh authorized inspection is separate from the previous outcome. The user can explicitly allow a separate decision after inspection; the earlier outcome remains unknown. Parsed and target-checked server responses are recorded independently of subsequent failed refreshes. Accepted receipts may be dismissed; unknown records are not automatically pruned. Some existing services lack an exact request-key reconciliation endpoint, so their current resource or bounded inventory is evidence for the user and cannot establish acceptance of a lost response. Moltbook cycle responses can include uncertain provider effects and remain inspection-only in the journal.

Three focused adapter cases cover recreation and explicit reconciliation, foreground closure during credential admission, and viewer/owner replacement rejection. Existing repository fixtures now return exact target identities and lifecycle states. Runtime validation is performed by the release coordinator; this implementation lane does not execute SDK or build commands.
