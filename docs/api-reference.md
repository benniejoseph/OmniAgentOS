# API and Configuration Reference

All routes are under `/api`. The canonical production origin is
`https://asael.bennierichard.com`. JSON is the default request/response format;
`/api/agent` returns server-sent events. Dynamic IDs are opaque strings and
callers must not infer tenancy from them.

## Authentication

- Browser sessions use the `__Host-asael_session` cookie in production and `asael_session` locally. Login sets `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` in production.
- `GET /api/auth/session` is safe to call anonymously and reports whether auth is enabled and whether the request is authenticated. Authenticated responses include only that session's private account label and exact tenant-bound identity.
- Internal automation sends `x-omni-internal-auth` with `OMNIAGENT_INTERNAL_AUTH_SECRET` plus explicit tenant, user, and role headers. Never accept those identity headers without the secret in production.
- Inbound MCP uses one-time-visible `asael_sk_...` service API keys created in Settings. Only a SHA-256 digest is stored. Existing `omni_sk_...` keys remain verifiable during the compatibility window. The verified key scope is intersected with the actor's enabled MCP export policy; neither layer can grant access by itself.
- Vercel cron uses `Authorization: Bearer <CRON_SECRET>` with `GET /api/workflows/tick`.
- The dedicated worker uses internal authentication with `POST /api/workflows/tick`.

Existing `OMNIAGENT_*`, `x-omni-*`, `x-omniagent-*`, and `omni_sk_...` names
remain stable wire and deployment compatibility contracts; they are not
product display names.

Viewer permissions cover protected reads. Operator permissions cover agent runs, workflows, evaluations, and routine tool actions. Admin permissions cover identity, connectors, security controls, and other high-risk configuration. Each route performs its own action-level authorization; a valid session alone does not guarantee access.

## Public and authentication routes

- `GET /api/health`: public liveness/readiness summary. Returns 200 for healthy or local degraded storage and 503 when a configured database is unhealthy.
- Public registration and access-request intake are disabled. `/signup` permanently redirects to `/login`.
- `GET|POST /api/onboarding/access-requests`: admin-only list and approve/decline workflow for historical requests in the Inbox.
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`, `GET /api/auth/google/authorize`, and `GET /api/auth/google/callback`. Password and Google admission both require an exact active entry in `OMNIAGENT_PRIVATE_ACCOUNT_ALLOWLIST_JSON`; Google may provision only that entry's immutable tenant after issuer, audience, nonce, expiry, and verified-email validation. Each entry declares `tenantMode: "existing" | "new"`; a `new` account fails closed if its tenant ID was already present. A removed/remapped entry, role drift, or an additional active membership invalidates existing browser and native sessions.
- `POST /api/mobile/auth/login`, `POST /api/mobile/auth/refresh`, `POST /api/mobile/auth/logout`, and `GET /api/mobile/bootstrap` provide the native opaque-token contract. Current clients attest normalized platform/version/build/contract metadata; legacy clients remain accepted but compatibility-unknown. All responses are private and no-store.
- `GET /api/mobile/contracts` discovers immutable OpenAPI, event-schema, fixture, and SHA-256 manifest documents under `/native-contracts/v{version}/`. Production advertises v29 as current and retains frozen v28 as the only rollback-compatible previous contract. V21 added the canonical Council read, v22 exact child cancellation, v23 the generic server-derived Inbox push cause, v24 the persistent prompt queue, v25 the Agent release/adaptation/task, schedule/PolicyLease, and notification-disposition management projections, v26 Daily Learning, v27 the governed command runner, v28 scoped Command model selection plus effective-model receipts, and v29 the authenticated Ambient Voice realtime session and versioned speech stream. V20-v27 remain byte-for-byte historical archives; v28 remains supported through the v29 rollback window. The generated Dart boundary references the same authoritative web routes for Android, iOS, and macOS and creates no parallel native business authority.
- `GET /api/mobile/adoption` is admin/system (`read.identity`) only and returns tenant-aggregate, PostgreSQL-authoritative native compatibility evidence. It never returns per-device or per-session identifiers and always reports Agent catalog enrollment as held.
- `GET /api/mobile/devices` and `POST /api/mobile/devices/:id` are native-bearer-only self-service routes for actor/tenant-scoped device inventory, revocation, and remote-wipe requests. They use the same native private/no-store and version headers as authentication routes.
- `GET|POST /api/mobile/push/canary` lists only the authenticated actor's eligible registrations and runs one idempotent live provider-to-app receipt canary. Its result keeps `providerState` (`queued`, `sending`, `accepted`, or `failed`) separate from `appState` (`none`, `received`, `opened`, or `action`); a provider acceptance is never reported as device delivery, and absence of an app receipt ends as an explicit timeout.
- `POST /api/mobile/push/deliveries/:id/receipts` is the native-v15 app-observation boundary. It requires the exact current installation, a stable stage-scoped `Idempotency-Key`, and `{schemaVersion:1, kind, action?, observedAt, appLifecycle}`. `action` is required only for an action receipt. The first observation for one key is retained across timestamp or lifecycle retries; reusing that key for another kind or action conflicts. Immutable actor-scoped receipts advance the legacy acknowledgement projection on open/action while preserving provider acceptance as a distinct fact. The legacy `/acknowledge` route remains a compatibility wrapper.
- `GET|POST /api/mobile/wipe` is a possession-bound remote-erasure handshake. GET returns a short-lived single-use challenge only to the exact revoked installation; POST can only acknowledge erasure and cannot restore or broaden authority.
- `GET|PUT /api/mobile/computer-use/device` reads or publishes this exact authenticated Mac installation's short-lived helper/permission readiness. `PUT` requires native capability `computer.use.device.update`, platform `macos`, contract v11 or later, a current native session, and both Accessibility and Screen Recording before `enabled` can become effective.
- `POST /api/mobile/computer-use/commands/claim` requires `computer.use.command.claim` and returns at most one exact queued command for the current actor, device, and mobile session. Optional `waitSeconds` from 0 through 20 keeps the private request open for a bounded long poll; it does not alter the claim lease or authority. The server reopens the sealed governed-tool input and verifies its digest; callers cannot create a local action through this courier.
- `POST /api/mobile/computer-use/commands/:id/complete` requires `computer.use.command.complete`, the exact device-bound unexpired claim token, and a bounded result. Identical completion retries return the same receipt. `POST /api/mobile/computer-use/stop` requires `computer.use.stop`, disables that device, stops its active sessions, and cancels queued or claimed commands. All four route groups are private/no-store.
- Flutter product writes continue through the existing `/api/agent`, `/api/approvals/:id`, `/api/today*`, `/api/projects*`, `/api/capture*`, `/api/notifications*`, and `/api/runs/:id` routes. A fresh bearer on the server-advertised current v29 or rollback v28 contract may enter only the route's registered native mutation capability and its independently pinned minimum version; all other native mutations remain held. `GET /api/artifacts` and `GET /api/artifacts/:id/content?version=` expose only the authenticated actor's verified generated files; they create no second artifact store and do not accept mutations. Meetings use the existing actor-visible `GET /api/meetings` and `GET /api/meetings/:id` projections. The Computer Use courier capabilities keep their independent v11 minimum and are accepted only from macOS; `local.macos.open_url`, screenshot presentation, and image-coordinate clicks additionally require the exact contract version declared by their tool contract.
- P12.4 offline Capture retries remain on `POST /api/capture`. A `capture-offline-*` idempotency key requires the identical `X-Omni-Correlation-Id` and the pinned `X-Asael-Capture-Owner-Sha256` digest of the native bootstrap tenant/actor. Any malformed or cross-session binding returns `409` before execution scope or multipart parsing. The retry therefore reuses deterministic asset and job identities; the headers grant no authority and ordinary bearer/RBAC/native-capability checks run first.
- `GET|POST /api/auth/control-plane`: admin-only tenant/user/membership administration. `POST` can create or rotate only an exact allowlisted identity in its policy-assigned tenant; it returns a generated initial password when one is not supplied.

## External A2A

- `GET /.well-known/agent-card.json` returns the minimal public Asael A2A Agent Card. `GET /api/a2a/extendedAgentCard` requires an active peer-bound service API key with `a2a:discover` and reveals only the local Agents allowed by that exact rollout.
- `GET|POST /api/a2a/peers` and `GET|PATCH /api/a2a/peers/:id` are authenticated owner-control APIs for reviewing, registering, listing, activating, pausing, and revoking exact peer generations. Registration performs SSRF-safe live discovery and pins HTTP+JSON `1.0`, the HTTPS interface, card and adapter digests, direction, credentials, allowlists, and hard limits. Outbound bearer material is sealed and never returned.
- `POST /api/a2a/message:send`, `POST /api/a2a/message:stream`, `GET /api/a2a/tasks`, and `GET|POST /api/a2a/tasks/:operation` implement the A2A 1.0 send, stream, list/get, subscribe, and cancel boundary. Requests require `A2A-Version: 1.0`, the A2A media type or JSON, a peer-bound service key with the exact discover/read/write scopes, trusted network/origin checks, and shared rate limits. Missing/older versions, redirects, URL/raw parts, mixed task coordinates, oversized content, inactive peers, and cross-owner references fail closed.
- `POST /api/a2a/delegated-tools/execute` accepts only the opaque task-scoped delegated Bearer token transported to an outbound peer. It requires the exact active rollout generation, unexpired token, working canonical task, live P8.7 safety lease, and allowlisted tool. Each distinct idempotency key atomically consumes one bounded append-only tool claim before invoking the normal governed executor with forced mutation approval; retries of that exact key are not charged twice. Responses are bounded redacted execution projections; raw delegated/provider credentials are never persisted or returned.

External messages, artifacts, and status remain untrusted observations. A remote `TASK_STATE_COMPLETED` maps only to canonical `completed_proposed`; only the existing exact parent verifier can record `result_accepted`.

Outbound dispatch rejects budgets above the fixed lower external authority,
repeated peers in canonical ancestry, exhausted depth/fan-out/root-task/root-cost
limits, and expired deadlines. The non-secret boundary is sent in message
metadata. Scheduled workflow maintenance closes stalled safety leases by
canceling the canonical task before its deadline or expiring it at the deadline.

## Agent, memory, and retrieval

- `POST /api/agent`: bounded message array and mode (`orchestrate`, `research`, `execute`, or `learn`); streams SSE events. Every new direct or Loop v2 run resolves its exact split Agent definition and security principal before execution and immutably binds their definition, persona, model-policy, prompt-contract, Skill, principal, and policy versions to the run. Recovery and clarification resume reload that existing pin instead of resolving current Agent state. The enrolled Loop v2 recent-runs canary may return a `clarification` event with `runId` and `threadId`, leaving that exact actor-owned run in `waiting_clarification` before any tool executes. An affirmative follow-up may include both IDs as `resumeRunId` and `threadId`; the server revalidates their actor/thread/agent binding and resumes under the original execution scope. A resume ID without its thread is invalid. Direct runs may send `contextScope` as `none`, `current_turn`, `session`, `agent_private`, `mission`, `project`, `workspace`, `personal`, or `explicit_selection`; only the last accepts `contextSelection`. Explicit selection must carry the exact query, ordered evidence IDs, and signed lock returned by `/api/retrieval/selection-lock`; stale, changed, cross-actor, or cross-tenant locks return `409`, and the raw lock is never persisted. Current-turn/no-extra-context requests discard supplied and stored history, while session keeps the actor-owned conversation but disables durable retrieval. Agent-private scope retrieves only records bound to the authenticated actor and exact assigned Agent, excludes tenant-wide memory/knowledge/graph stores, emits no private query trace, and disables sibling council delegation. Project and Workspace scope require exact canonical membership. Mission scope requires an attached owned Mission, resolves its compatibility ID to that exact canonical Project membership, and does not create a separate Mission memory store. Personal scope requires the exact authenticated owner's active, versioned standing-consent generation; it retrieves only canonical owner-private coordinate-free memory, emits no private query trace, disables tools, web search, sibling council delegation, and response consolidation, and must persist the shrink-only automatic compiler receipt before model disclosure. Workflow plan/start accepts Mission, Project, and Workspace scope with the corresponding coordinate, Agent-private scope with an exact `agentId`, and Personal scope with current owner consent. Planning stores only the relevant content-free authority digest. Start discards caller-supplied private bindings, creates a server-only envelope bound to the immutable workflow root, and public projections remove it. Durable retrieval, every later step, and every plan/replan revalidate current membership, Agent identity/grants, or the exact consent generation and fail if root authority, expiry, membership, identity, grants, consent, or the reviewed plan boundary changed. Agent-private and Personal database access always has null Workspace, Project, and Mission coordinates. A non-empty, query-matched `contextSelection` authorizes only that direct request to compile the authenticated canonical user's selected private-memory IDs in personal `all` mode. Context Compiler v2 intersects that legacy-selected set with independently authorized evidence and may only remove candidates; its metadata-only canary receipt must persist on the actor-bound run before the provider call. Receipt failure blocks disclosure. An explicit user-private selection exposes no tools and skips legacy prompt/response consolidation. Personal durable access exists only through its server-created root-bound envelope and current consent; no background worker receives a free-standing private prompt grant.
- `GET /api/command/catalog` returns the authenticated actor's private/no-store, partially available catalog of selectable Agents, Skills, enabled Extensions, Projects, connected Integrations, and ready Library files; only ready files are selectable. A direct `POST /api/agent` may carry the resulting bounded `contextReferences`; the server ignores caller labels, re-resolves every ID and version/digest binding, enforces a single primary Agent and Project, and records only content-free pins. File revalidation resolves the exact Library authority and source ID under canonical/exact actor readability and fails closed on duplicate or mismatched projections. These references add guidance or source data but no tool, OAuth, filesystem, delegation, membership, or mutation authority. Ready Capture files may contribute verified bounded indexed evidence or verified text as untrusted model input after current-content and extraction-integrity checks. An actor-private connected source may contribute a bounded verified cognition excerpt only when its current source item, revision, document, purpose, retention, content hash, chunks, and evidence lineage agree. Shared, metadata-only, unlinked, binary, and integrity-ineligible sources do not inject a body. Changed references fail with `409`, missing references with `404`, and unavailable revalidation with `503`. Ephemeral references are direct-run only and are not accepted by workflow planning or the persistent prompt queue.
- `GET|POST /api/command/prompt-queue`, `PATCH|DELETE /api/command/prompt-queue/:id`, and `POST /api/command/prompt-queue/reorder` manage the authenticated actor's persistent Command queue. Create accepts one bounded prompt, mode, direct/auto strategy, exact Agent ID, stable client correlation ID, and strict Conversation/Mission/Project plus `asael|local_macos` target. The server seals prompt text, resolves and pins the exact Agent definition/principal and configured provider/model route, caps the active queue at 40, and returns `409` for stale revisions or correlation reuse with changed intent. Reorder must name the complete queued/paused set and is atomic. Queue operations never grant execution, context, tools, approvals, budgets, or Computer Use authority. Queue identity is deliberately split: the canonical authenticated `omni_auth_users.actor_id` owns storage, RLS, sealing, lifecycle, and dispatch admission, while the request actor remains only the compatibility coordinate for resolving existing Agent, Settings, and model-routing pins and reading the exact legacy-owned run during stale-lease reconciliation. Neither identity is accepted from the request body, and a session without a canonical account binding fails before queue mutation or dispatch.
- `POST /api/command/prompt-queue/:id/dispatch` accepts the exact lifecycle revision and optional explicit `force` for a paused item, then streams the ordinary governed `/api/agent` SSE response. Authentication runs before production-origin validation, origin validation runs before claim, and dispatch revalidates Agent/model pins before binding a short-lived one-time raw token to the current native/browser session. After admission leaves its database request scope, the route performs a separate canonical HTTPS request to `/api/agent`; it overwrites the queue ID/token and active release-revision headers, strips forwarding and hop-by-hop headers, refuses cross-origin redirects, requires a successful SSE response, and fails the claim closed when the active release differs. `/api/agent` independently re-derives the canonical owner, consumes the exact sealed prompt/mode/strategy/Agent/target admission once, and persists run-link and terminal receipts in its event loop before exposing those events. Terminal completion, failure, cancellation, approval/clarification wait, or durable delegation clears the dispatch token and lease. Disconnect or lease expiry never blindly replays work: a durable run ID reconciles to its canonical run state, while absence of a durable link records failure and requires an actor resume. Web and native clients consume the same states; the native encrypted offline outbox replays original correlations/revisions and reports conflicts instead of overwriting newer server state.

- Native v28 may send strict optional `modelSelection` on a fresh `/api/agent` request. It is unavailable for resume and durable execution; an explicit selection forces direct execution and disables team fan-out, while an explicit built-in or custom Agent remains authoritative. The server revalidates the exact assignment ID, revision, configuration SHA-256, scope, provider, model, lifecycle/capability readiness, connection, credential, and supported reasoning intensity. Selection evidence persists only a content-free `commandSelectionSha256` plus effective provider/model/reasoning receipt fields; prompt content and private reasoning are excluded. A conflicting durable explicit-selection request returns private/no-store `409` before model execution.

- `POST /api/agent` accepts optional `computerUseTarget: "local_macos" | "isolated_browser"` only as a transition-compatible request shape. Omission carries no local-control grant and no prompt text can infer **This Mac**. `local_macos` is accepted only from an authenticated compatible macOS client, starts an exact tenant/actor/correlation/run-bound session, selects the direct agent path, and exposes only the closed `local.macos.*` allowlist. The submitted natural-language objective authorizes only the same run's bounded navigation, selection, media-control, and non-sensitive text-entry steps; visual actions are serialized and consume the run's visual-action budget. Submit, transfer, destructive, financial, account/security, permission, unknown, broad modified-shortcut, and direct-command effects retain ordinary per-action approval. Post-action screenshot and Accessibility evidence is one-turn-only and never enters the durable continuation. `isolated_browser` is retired: new requests return `410 computer_use_target_retired`, saved continuations fail closed with a typed `execution_target_retired` run event, and neither path redirects to **This Mac**. The former browser profile, takeover, activity, frame, snapshot, and stream product routes return `410`; retained database rows are audit history, not API or execution authority. App Builder's separate legacy browser-evidence field remains readable as non-gating history.
- `GET /api/memory/personal-context-consent`: returns the authenticated canonical owner's current `inactive | active` state, exact versioned notice, and content-free active authority projection with private, no-store caching.
- `POST /api/memory/personal-context-consent`: activates a new owner-only consent generation only when the client acknowledges the exact current notice contract, version, and SHA-256 digest. The governed mutation emits `memory.personal_context_consent.activated`.
- `DELETE /api/memory/personal-context-consent`: revokes the caller's exact active generation and emits `memory.personal_context_consent.revoked`; history remains immutable and a later opt-in creates a new generation.
- `GET|POST /api/agents` and `GET|PATCH|DELETE /api/agents/:id` manage the compatibility projection for custom Agents. PostgreSQL mutations atomically version behavioral definition fields separately from principal authority fields; custom Skill changes version each affected definition. `GET /api/agents/:id?mode=trash-preview` returns the exact expiring removal preview, and DELETE accepts only that preview before retiring the principal and moving the resource to Trash. Bare list GET remains exact-owner and marks its custom rows actionable; `GET /api/agents?ownerScope=readable` is the request-bound compatibility list used by Arsenal and the web Mission workspace. Detail GET and the compatibility list add `selectable` and `manageable`: exact-owner rows are actionable, while canonical compatibility rows are read-only and cannot enter Command, Mission assignment, or native mutation controls. Agent creation and updates return `409` when any selected custom Skill is unavailable to the Agent's exact persisted tenant/actor owner.
- `GET /api/agents/cards` returns the authenticated caller's five internal built-in `p8.5-agent-card:1` projections with private/no-store caching. Cards advertise exact definition identity, closed input/output schemas and their digests, semantic task kinds, modalities, tool policy, delegated-principal authentication requirements, protocol versions, and hard limits. They never include tenant/actor coordinates, execution principals, grants, endpoints, tokens, or credentials and do not enable external A2A. Supplying bounded `query` and `taskKind=general|coordinate|research|build|verify|memory` returns a deterministic, non-authoritative compatibility-ranked discovery receipt.
- `GET|POST /api/agents/:id/grants` lists or creates exact context and capability grants for one owned, manageable custom Agent; `DELETE /api/agents/:id/grants/:grantId` revokes one pinned grant. All responses are private/no-store and require canonical actor identity plus workflow-management authority. Create accepts a strict typed purpose, visibility, exact target/resource and operation IDs, bounded item/byte/invocation/cost/duration budgets, and an expiry from five minutes through one year. Every mutation rotates the Agent principal, reissues retained live grants to the new generation, revokes the prior generation and grants, pins the new exact grant IDs, and emits metadata-only held/activated/revoked events. Revocation first resolves the request-attributed preview and submits that exact target digest through the same application-service boundary used by governed tools; it never mutates the grant store directly. Equivalent, stale, cross-owner, expired, wildcard, or unpinned requests fail closed. Built-in and readable compatibility Agents cannot be widened through these routes.
- `GET|POST /api/agents/:id/release` reads or transitions one exact-owner custom Agent release. `POST` accepts only `evaluate`, `promote`, `rollback`, or `retire`: evaluation names the candidate definition version; promotion and rollback name an immutable evaluation bound to the current active baseline; retirement requires the literal confirmation `RETIRE AGENT`. Retirement first resolves the request-attributed preview and submits its exact target digest through the same application-service boundary used by governed tools; the service rechecks the preview before the terminal mutation. Responses are private/no-store and require canonical actor identity plus workflow-management authority. Native v25 enrolls only `evaluate`, `promote`, and `rollback`; a native retirement request has no mutation capability and fails closed, while the separately reviewed web control retains retirement. Draft updates never become executable implicitly, stale transitions return `409`, retirement is terminal, and built-in or readable compatibility Agents cannot use this route.
- `GET /api/agents/tasks/:id` returns one authenticated actor's private/no-store delegation-task detail through `app.agents.tasks.show`. It exposes the public task projection, immutable contract and grant-request digests, exact safe Skill version, Plugin installation/component, MCP server/tool, and native-read tool pins, a durable content-free grant-validation state (`not_checked`, `current`, or `changed`), source-management links, and a cancel control only while the task is cancellable. Raw manifests, credentials, private prompt/persona guidance, exception text, and mutable grant controls are excluded. A missing durable validation receipt is reported as `not_checked`; it is never inferred to be current. Worker validation re-resolves every exact grant, persists the typed metadata-only receipt before claiming a task, and fails closed if a binding changed or the receipt cannot be written. An optional dynamic child persona contains only a bounded label/guidance, is digest-bound to the child prompt with `authorityEffect: "none"`, and cannot change identity, model, grants, tools, budgets, approval, scope, or redelegation policy.
- `GET|POST /api/agents/:id/adaptations` reads or transitions the canonical actor's evidence-gated adaptations for the exact current Agent identity. GET returns the current `definitionVersion` and private lifecycle records. POST accepts only explicit `refresh`, `evaluate`, `activate`, or `rollback`; the latter three require the exact deterministic `adaptationId`. Refresh observes owner corrections without activating them, evaluation is bound to the observed/current release and versioned policy, activation requires a passed exact-release evaluation and assigns a monotonic version, and rollback is terminal. The proactive maintenance lane may propose an `observed` candidate only from an exact-version deterministic evidence set covering corrected runs, verified Project artifacts, governed delegated outcomes, and governed schedule outcomes. It pins the target and Sentinel identities plus configured verifier runtime, records a separate Sentinel review, and never evaluates or activates its proposal. Only an explicit owner lifecycle action can make exact-release guidance active, and every effect remains non-authority instruction guidance.
- `GET /api/agents/:id/learning` returns the authenticated owner’s content-free Daily Learning status for the Agent’s exact current definition: latest completed local day, reviewed-work counts, explicit correction/actionable-evidence counts, and whether a passed reviewed adaptation is waiting for activation. It never returns prompts, responses, correction text, or private reasoning.
- Each Agent definition has one strict persona object containing charter, operating style, voice, visual identity, allowed domains, escalation behavior, and success measures. Older compatible create payloads receive the conservative default persona, while updates replace the full object. Persona content remains untrusted behavior and cannot grant authority.
- `GET|POST /api/skills` and `GET|PATCH|DELETE /api/skills/:id` manage the Skill catalog. The built-in starter library includes focused playbooks for research, memory, productivity, project and meeting work, decision-making, product design, accessibility, visual critique, implementation, debugging, review and security, testing and performance, writing, workflow design, and knowledge synthesis. A custom Agent can compose at most eight Skills so every assigned playbook is present in both its prompt and governed-tool allowlist; create and update reject larger assignments instead of silently omitting instructions. `GET /api/skills/:id?mode=trash-preview` returns the exact expiring removal preview, and DELETE accepts only that preview before moving the custom Skill and its surviving assignment snapshot to Trash. Request reads add `selectable` and `manageable` capability flags: built-ins are selectable but not manageable, exact-owner custom Skills are both, and canonical compatibility rows are read-only and cannot be assigned. A Skill can reference governed Tools for an assigned agent, but cannot bypass the executor's tenant, actor, approval, risk, or idempotency policy.
- `GET /api/plugins` returns the private/no-store declarative Plugin v1 catalog, the current actor's installation projections, lifecycle summary, exact manifests and SHA-256 digests, and explicit activation truth. `activation.skillsActive` means actual actor-owned Skills are active; it never implies that an MCP credential, connection, or contract is ready. An enabled Plugin projects its declared Skills into the existing actor-owned Skill catalog with tenant/actor-derived stable IDs; disabling or uninstalling it disables those Skills, and Plugin-projected Skills cannot be edited or moved to Trash independently. V1 does not perform in-place upgrades: `updateAvailable` remains false, while `updateRequiresUninstall` truthfully flags an installed catalog digest mismatch. `POST /api/plugins/preview` accepts either an exact curated `{pluginId, version, manifestSha256}` or a strict declarative `manifest` and persists a 15-minute actor-private preview. `POST /api/plugins/install` accepts only `{previewId, manifestSha256}` from that unexpired exact preview. `PATCH /api/plugins/:id` accepts `{action:"enable"|"disable", expectedRevision}` and `DELETE /api/plugins/:id` accepts `{expectedRevision}`; uninstall is a retained reversible lifecycle state and a later install still requires a fresh exact preview. Every mutation requires an `Idempotency-Key`, workflow-management authority, and a matching tenant/actor execution scope. Manifests may contain only bounded Skill templates, external MCP connection templates, and metadata-only workflow templates—never executable code or credentials. Plugin installation creates no MCP connector, stores no token, authorizes no MCP contract or tool, starts no workflow, and bypasses no connector review, governed execution, approval, or idempotency boundary.
- `/api/runs` and `/api/runs/:id`: actor-private run history, events, and replay/continuation state. PostgreSQL enforces the authenticated owner boundary across the run, its thread/turns, event streams, checkpoints, resume claims, identity pin, and fork lineage; sibling actors in the same tenant cannot inspect them. Run detail returns `contextReceipt` when the runner persisted `run.context.receipt`: a content-free comparison of previewed, included, excluded, actually-used, and selected-but-dropped evidence IDs plus manifest/context/budget digests. `GET /api/runs/:id/trajectory` returns trajectory v3 with bounded event receipts, `outcomeEvidence`, a non-activating `outcomeEvaluation`, checkpoint steps, structural verification, parent/child fork lineage, that receipt's bounded metadata, `traceHierarchy`, and the pinned `p11.2-conversation-progress:1` `conversationProgress` projection. The latter unifies request, plan, context, Agent, model, governed-tool, browser, voice, approval, evidence, result, and actionable recovery state from owner-scoped durable events, exact thread voice events, and checkpoints. Every progress item carries a hashed event reference or exact checkpoint metadata; raw prompts, responses, tool payloads, credentials, retrieved content, outputs, and private reasoning are excluded. `/app/command?run=<id>` resolves the owned thread and opens this exact historical or current activity record. `POST /api/runs/:id/fork` accepts an exact `checkpointId`, a 1–4,000 character correction, and an optional bounded `requestId`/matching `Idempotency-Key`; it creates and executes a new owner-bound trace from the verified event prefix. The source trace is immutable, and the fork starts with a fresh execution scope, a newly resolved exact Agent identity, no inherited continuation, and no inherited approval. `GET /api/runs/:id/activity/stream` is a private/no-store server-sent projection that pushes owner-scoped browser actions and observation metadata and labels the persisted run `live` or `replay`. Legacy `work`-purpose rows remain rollback-readable in storage but cannot be newly authorized or surfaced as the current account's connection.
- Tool execution records validate a present canary `effectReceipt` against the execution, tenant, actor, and `memory.write` tool bindings before returning it. Legacy records, dry runs, direct tool calls, and other tools omit the field and keep their existing response behavior. The canary covers the first-party memory-store commit acknowledgement and tenant-scoped read-after-write only; it is not full P1.4 external-effect support.

It accepts service-key Bearer authentication only, requires MCP to be enabled in Settings, rate-limits by tenant and key, and initially exports read-only memory, knowledge, mission, and run tools. Every call still uses the governed tool executor and durable tool audit. `GET` and `DELETE` return `405`.

Credential plaintext is accepted only on create/rotation and is never returned after storage. `GET /api/settings/providers?ownerScope=readable`, `GET /api/settings/assignments?ownerScope=readable`, `GET /api/settings/mcp?ownerScope=readable`, and `GET /api/settings?ownerScope=readable` opt their public metadata into strictly bound canonical/current-email reads; bare GETs stay exact. Successful provider, assignment, and MCP metadata responses acknowledge independent `requestReadContracts` entries as `readable_v1` or `exact_v1`; clients must require the matching readable contract before exposing writes. Provider rows include `manageable`; canonical connections are configuration-only and read-only, deployment fallbacks remain externally managed, and credential ciphertext/key IDs are never selected by the request reader. Assignment rows include `manageable` plus render-safe model identifiers; canonical routes are configuration-only, occupy their scope as a read-only continuity record, and never seed editable provider, fallback, or consent state. Authenticated model-catalog GETs may merge the same owners; `selectable` is true only for exact-owner identifiers accepted by the assignment API, while `displayModelId` is the safe UI projection of the persisted identifier. Authenticated service-key GETs select redacted columns and expose physical-owner-derived `manageable`. Request-readable MCP metadata selects only the public policy allowlist; a retained canonical policy is visible but cannot seed or authorize a save. Provider credential opening, validation, rotation, updates/revocation, catalog refresh, runtime model resolution, assignment PUT/pre-read, MCP PUT/pre-read and runtime policy resolution, key creation/revocation, Bearer verification, and last-used updates remain exact-owner operations.

Catalog display grants no execution authority; `/api/agent` independently revalidates the complete assignment and provider boundary before use.

## Common status codes

- `400`: body/schema validation failed.
- `401`: authentication is required or invalid.
- `403`: authenticated identity lacks the required action/role.
- `404`: resource is absent or intentionally hidden across tenant boundaries.
- `409`: state transition conflict.
- `413`: request body exceeds the configured limit.
- `429`: a shared Postgres-backed safety limit was reached (single-process fallback is used only outside durable deployments).
- `503`: production storage, cron, or a required dependency is unavailable.

## Configuration precedence and safety

Application configuration comes from process environment variables. `NEXT_PUBLIC_*` values are embedded into browser bundles at build time; everything else must remain server-only. Set the production `NEXT_PUBLIC_APP_URL` to exactly `https://asael.bennierichard.com`. Vercel supplies deployment metadata through `VERCEL_*`. The worker reads `OMNIAGENT_WORKER_BASE_URL`, then `NEXT_PUBLIC_APP_URL`, then `BASE_URL`.

Use `.env.example` for the full supported list and defaults. Production-required values and operational smoke credentials are separated there. Smoke-only `SMOKE_*` values belong in the CI secret store, not in the web deployment. See [deployment.md](deployment.md) for rollout and rotation guidance.
