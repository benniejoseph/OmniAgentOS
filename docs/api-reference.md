# API and Configuration Reference

All routes are under `/api`. The canonical production origin is
`https://asael.bennierichard.com`. JSON is the default request/response format;
`/api/agent` returns server-sent events. Dynamic IDs are opaque strings and
callers must not infer tenancy from them.

## Authentication

- Browser sessions use the `__Host-asael_session` cookie in production and `asael_session` locally. Login sets `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` in production.
- `GET /api/auth/session` is safe to call anonymously and reports whether auth is enabled and whether the request is authenticated. Authenticated responses include only that session's private account label and exact tenant-bound identity.
- Internal automation sends explicit tenant, user, and role headers with `x-omni-internal-auth`. The dedicated worker puts a five-minute token there, signed with a key derived from `OMNIAGENT_INTERNAL_AUTH_SECRET` for those exact headers and the request's method and path, so the secret never leaves the worker. The release scripts still send the secret itself, because they also verify the release being replaced. Never accept those identity headers without a valid token or the secret in production.
- Live CLI agent evaluations and expanded checkpoint checks sign in through `POST /api/auth/login` and use the issued session cookie plus the trusted application `Origin`; internal identity headers cannot select the owner of a live agent turn. `EVAL_TENANT_ID`/`EVAL_ACTOR_ID` and `SMOKE_TENANT_ID`/`SMOKE_ACTOR_ID` are assertions about the signed-in identity, never scope overrides. Both runners attempt `POST /api/auth/logout` even after a failed check.
- Inbound MCP uses one-time-visible `asael_sk_...` service API keys created in Settings. Only a SHA-256 digest is stored. Existing `omni_sk_...` keys remain verifiable during the compatibility window. The verified key scope is intersected with the actor's enabled MCP export policy; neither layer can grant access by itself.
- Vercel cron uses `Authorization: Bearer <CRON_SECRET>` with `GET /api/workflows/tick`.
- The dedicated worker uses internal authentication with `POST /api/workflows/tick`.

Existing `OMNIAGENT_*`, `x-omni-*`, `x-omniagent-*`, and `omni_sk_...` names
remain stable wire and deployment compatibility contracts; they are not
product display names.

Viewer permissions cover protected reads. Operator permissions cover agent runs, workflows, evaluations, and routine tool actions. Admin permissions cover identity, connectors, security controls, and other high-risk configuration. Each route performs its own action-level authorization; a valid session alone does not guarantee access.

## Change idempotency

Every route that changes state through the application services shared with governed Agent tools requires an `Idempotency-Key` header: an opaque identifier of 1–512 letters, numbers, or `. _ : @ / + ~ -` that starts with a letter or number. A change without a valid key returns `400` before it is authenticated or authorized. The server never makes a key up and never takes one from `X-Request-Id` or `X-Idempotency-Key`, because both differ on every retry and the change would run again. Retry a change with its original key; a new user action takes a new key. The key is also the change's correlation id (a SHA-256 digest when it is longer than 256 characters), so identifiers derived from the correlation repeat on retry. `X-Request-Id` is only the correlation id of a read. A route may narrow the key format further, as noted below. Mission routes still fall back to the request id when the key is missing.

## Public and authentication routes

- `GET /api/health`: public liveness/readiness summary. Returns 200 for healthy or local degraded storage and 503 when a configured database is unhealthy. Responses carry the served `revision` and, on a deployment the release runner made, the `releaseManifest` it signed for that deployment.
- `GET /api/health/worker`: public monitor of the dedicated worker for this deployment's revision. For each of the fast, background, and maintenance lanes it reports `fresh`, `stale`, or `missing` and the age of the lane's last release work on any worker machine; a lane that has not worked yet counts from its machine's activation. Returns 200 only when every lane is fresh within `OMNIAGENT_WORKER_HEARTBEAT_MAX_AGE_MS` and 503 otherwise, including while a release is held; a failed read returns 503 with `status: "unknown"`. It names no machine. `/api/health` does not depend on the worker, because the worker and the release runner read it before any work starts.
- Public registration and access-request intake are disabled. `/signup` permanently redirects to `/login`.
- `GET|POST /api/onboarding/access-requests`: admin-only list and approve/decline workflow for historical requests in the Inbox.
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`, `GET /api/auth/google/authorize`, and `GET /api/auth/google/callback`. Password and Google admission both require an exact active entry in `OMNIAGENT_PRIVATE_ACCOUNT_ALLOWLIST_JSON`; Google may provision only that entry's immutable tenant after issuer, audience, nonce, expiry, and verified-email validation. Each entry declares `tenantMode: "existing" | "new"`; a `new` account fails closed if its tenant ID was already present. A removed/remapped entry, role drift, or an additional active membership invalidates existing browser and native sessions.
- `POST /api/mobile/auth/login`, `POST /api/mobile/auth/refresh`, `POST /api/mobile/auth/logout`, and `GET /api/mobile/bootstrap` provide the native opaque-token contract. Current clients attest normalized platform/version/build/contract metadata; legacy clients remain accepted but compatibility-unknown. All responses are private and no-store.
- `GET /api/mobile/contracts` discovers immutable OpenAPI, event-schema, fixture, and SHA-256 manifest documents under `/native-contracts/v{version}/`. The current contract is v33, with frozen v32 as the supported previous contract and frozen v31 as an unadvertised archive. V31 added owner-bound Companion preferences; v32 added ten typed Responsibility operations. V33 replaces the two generic Meeting reads with typed envelopes, adds commitment reads and publishes four existing scoped Meeting mutations. Only v33 documents are generated; v31/v32 bytes remain unchanged and v30 leaves the archive window. The generated Dart boundary uses the same authoritative web routes on Android, iOS and macOS and creates no parallel native business authority.
- `GET /api/mobile/adoption` is admin/system (`read.identity`) only and returns tenant-aggregate, PostgreSQL-authoritative native compatibility evidence. It never returns per-device or per-session identifiers and always reports Agent catalog enrollment as held.
- `GET /api/mobile/devices` and `POST /api/mobile/devices/:id` are native-bearer-only self-service routes for actor/tenant-scoped device inventory, revocation, and remote-wipe requests. They use the same native private/no-store and version headers as authentication routes.
- `GET|POST /api/mobile/push/canary` lists only the authenticated actor's eligible registrations and runs one idempotent live provider-to-app receipt canary. Its result keeps `providerState` (`queued`, `sending`, `accepted`, or `failed`) separate from `appState` (`none`, `received`, `opened`, or `action`); a provider acceptance is never reported as device delivery, and absence of an app receipt ends as an explicit timeout.
- `POST /api/mobile/push/deliveries/:id/receipts` is the native-v15 app-observation boundary. It requires the exact current installation, a stable stage-scoped `Idempotency-Key`, and `{schemaVersion:1, kind, action?, observedAt, appLifecycle}`. `action` is required only for an action receipt. The first observation for one key is retained across timestamp or lifecycle retries; reusing that key for another kind or action conflicts. Immutable actor-scoped receipts advance the legacy acknowledgement projection on open/action while preserving provider acceptance as a distinct fact. The legacy `/acknowledge` route remains a compatibility wrapper.
- `GET|POST /api/mobile/wipe` is a possession-bound remote-erasure handshake. GET returns a short-lived single-use challenge only to the exact revoked installation; POST can only acknowledge erasure and cannot restore or broaden authority.
- `GET|PUT /api/mobile/computer-use/device` reads or publishes this exact authenticated Mac installation's short-lived helper/permission readiness. `PUT` requires native capability `computer.use.device.update`, platform `macos`, contract v11 or later, a current native session, and both Accessibility and Screen Recording before `enabled` can become effective.
- `POST /api/mobile/computer-use/commands/claim` requires `computer.use.command.claim` and returns at most one exact queued command for the current actor, device, and mobile session. Optional `waitSeconds` from 0 through 20 keeps the private request open for a bounded long poll; it does not alter the claim lease or authority. The server reopens the sealed governed-tool input and verifies its digest; callers cannot create a local action through this courier. A press, click, key, or type that runs on This Mac task authority alone is delivered only to a v30 or later client, marked `authority: "task"`; for an older client the claim fails that command with `task_authority_unattested` and the executor offers it as a fresh approval. A v30 helper that finds the target outside task authority completes the command with `task_authority_refused`, which the executor also offers for review.
- `POST /api/mobile/computer-use/commands/:id/complete` requires `computer.use.command.complete`, the exact device-bound unexpired claim token, and a bounded result. Identical completion retries return the same receipt. `POST /api/mobile/computer-use/stop` requires `computer.use.stop`, disables that device, stops its active sessions, and cancels queued or claimed commands. All four route groups are private/no-store.
- Flutter product writes use the existing authoritative product routes. A fresh native bearer on current v33 or previous v32 may enter only a registered mutation capability at its separately pinned minimum version. Responsibility mutations retain floor 32, Companion preferences retain floor 31, and the three new Meeting capabilities require 33: `meetings.records.manage` for create/revise, `meetings.commitments.propose` for exact media proposals, and `meetings.commitments.resolve` for reviewed decisions. Original RBAC, workspace authority, consent, replay identity and child-effect governance still apply. V32 cannot enter Meeting writes. The three published Meeting GETs return bounded typed scope, revision, source and receipt evidence. Calendar sync, recording completion and source-audio access are not enrolled by this publication. `GET /api/artifacts` and exact-version content reads remain actor-scoped. Computer Use keeps its independent v11 minimum and macOS-only enrollment; individual tools may require a later exact version.
- P12.4 offline Capture retries remain on `POST /api/capture`. A `capture-offline-*` idempotency key requires the identical `X-Omni-Correlation-Id` and the pinned `X-Asael-Capture-Owner-Sha256` digest of the native bootstrap tenant/actor. Any malformed or cross-session binding returns `409` before execution scope or multipart parsing. The retry therefore reuses deterministic asset and job identities; the headers grant no authority and ordinary bearer/RBAC/native-capability checks run first.
- `GET|POST /api/auth/control-plane`: admin-only tenant/user/membership administration. `POST` can create or rotate only an exact allowlisted identity in its policy-assigned tenant; it returns a generated initial password when one is not supplied.

## External A2A

- `GET /.well-known/agent-card.json` returns the minimal public Asael A2A Agent Card. `GET /api/a2a/extendedAgentCard` requires an active peer-bound service API key with `a2a:discover` and reveals only the local Agents allowed by that exact rollout.
- `GET|POST /api/a2a/peers` and `GET|PATCH /api/a2a/peers/:id` are authenticated owner-control APIs for reviewing, registering, listing, activating, pausing, and revoking exact peer generations. Registration performs SSRF-safe live discovery and pins HTTP+JSON `1.0`, the HTTPS interface, card and adapter digests, direction, credentials, allowlists, and hard limits. Outbound bearer material is sealed and never returned.
- `POST /api/a2a/message:send`, `POST /api/a2a/message:stream`, `GET /api/a2a/tasks`, and `GET|POST /api/a2a/tasks/:operation` implement the A2A 1.0 send, stream, list/get, subscribe, and cancel boundary. Requests require `A2A-Version: 1.0`, the A2A media type or JSON, a peer-bound service key with the exact discover/read/write scopes, trusted network/origin checks, and shared rate limits. Missing/older versions, redirects, URL/raw parts, mixed task coordinates, oversized content, inactive peers, and cross-owner references fail closed. A task's result artifact appears only after the parent accepts the contribution, and it is marked `untrusted: true` and `independentlyVerified: false`: acceptance checks the result's shape and contract binding, not whether its content is true, so a task that completes carries `resultDisposition: structurally_accepted`. Sentinel takes no inbound task. A new rollout cannot allow it, the extended card omits it, and a request for it returns 403. A new task is metered and budgeted per peer before it is submitted: past the peer's hourly task starts, or when the task's budget would not fit the peer's or the workspace's AI usage over the last 24 hours, the request returns 429 `resource_exhausted`, and it returns 503 when that usage cannot be read. A retry of an existing message is not charged again.
- `POST /api/a2a/delegated-tools/execute` accepts only the opaque task-scoped delegated Bearer token transported to an outbound peer. It requires the exact active rollout generation, unexpired token, working canonical task, live P8.7 safety lease, and allowlisted tool. Each distinct idempotency key atomically consumes one bounded append-only tool claim before invoking the normal governed executor with forced mutation approval; retries of that exact key are not charged twice. Responses are bounded redacted execution projections; raw delegated/provider credentials are never persisted or returned.

External messages, artifacts, and status remain untrusted observations. A remote `TASK_STATE_COMPLETED` maps only to canonical `completed_proposed`; only the existing exact parent verifier can record `result_accepted`.

Outbound dispatch rejects budgets above the fixed lower external authority,
repeated peers in canonical ancestry, exhausted depth/fan-out/root-task/root-cost
limits, and expired deadlines. The non-secret boundary is sent in message
metadata. Scheduled workflow maintenance closes stalled safety leases by
canceling the canonical task before its deadline or expiring it at the deadline.

## Agent, memory, and retrieval

- `GET|PATCH /api/companion/preferences` uses the private/no-store `asael-companion-preferences:1` contract for the authenticated tenant and actor. GET returns an unsaved revision-0 default without creating a row. PATCH requires `manage.own_preferences`, normal trusted-origin checks, an `Idempotency-Key`, and either `{action:"save",expectedRevision,preferences}` with all five fields (`intensity`, `visible`, `motion`, `defaultDestination`, `preferredThreadId`) or `{action:"reset",expectedRevision}`. Compare-and-swap conflicts return 409; an exact replay returns its immutable mutation receipt separately from the current snapshot, which may be newer. Changed preferred homes must identify an owned UUID thread. Deleted or inaccessible homes retain the saved ID and revision but resolve to the Assistant fallback; an unconfirmed read cannot establish availability. Preferences change presentation and entry destinations only and grant no execution authority. Native PATCH requires the separately registered `companion.preferences.update` capability, a fresh compatible attestation and contract v31 or later. Native GET and PATCH also require `X-Asael-Companion-Owner-Sha256`, the lowercase SHA-256 of UTF-8 `asael.companion-owner:1\0<tenantId>\0<actorId>` (the separators are NUL bytes). The digest narrows the already authenticated tenant/actor and never selects an owner; a missing or mismatched native binding returns 409 before store access. When supplied by a web caller the same binding is checked. The unchanged v30 rollback contract does not enroll this new mutation. Migration v215 supplies owner-scoped RLS, atomic revision changes and immutable receipts; development file storage uses the same contract, while production without PostgreSQL fails closed.

- `GET /api/activity` returns the private/no-store `asael-activity:1` read projection. `group=all|working|needs_you|updates|history`, `limit=1..50` (default 25) and an opaque `cursor` select a page within at most 100 recent records per source. Runs require the caller's exact or validated canonical ownership and independent thread access; approval reads additionally require `manage.workflow`; reminder reads retain actor scope and do not process due notifications. Counts describe only the current readable window. `coverage` distinguishes ready, partial, restricted and unavailable sources; unavailable sources never mean zero lifetime work. Cursors bind the authorized scope, filter, page size and current projection; changed access or source content returns 409 with `activity_cursor_stale` and `reload:true`. Only bounded metadata and canonical source links are returned, with no prompts, output bodies, approval inputs or new execution storage.

- `POST /api/agent`: bounded message array and mode (`orchestrate`, `research`, `execute`, or `learn`); streams SSE events. Every new direct or Loop v2 run resolves its exact split Agent definition and security principal before execution and immutably binds their definition, persona, model-policy, prompt-contract, Skill, principal, and policy versions to the run. Recovery and clarification resume reload that existing pin instead of resolving current Agent state. The enrolled Loop v2 recent-runs canary may return a `clarification` event with `runId` and `threadId`, leaving that exact actor-owned run in `waiting_clarification` before any tool executes. An affirmative follow-up may include both IDs as `resumeRunId` and `threadId`; the server revalidates their actor/thread/agent binding and resumes under the original execution scope. A resume ID without its thread is invalid. Direct runs may send `contextScope` as `none`, `current_turn`, `session`, `agent_private`, `mission`, `project`, `workspace`, `personal`, or `explicit_selection`; only the last accepts `contextSelection`. Explicit selection must carry the exact query, ordered evidence IDs, and signed lock returned by `/api/retrieval/selection-lock`; stale, changed, cross-actor, or cross-tenant locks return `409`, and the raw lock is never persisted. Current-turn/no-extra-context requests discard supplied and stored history, while session keeps the actor-owned conversation but disables durable retrieval. Agent-private scope retrieves only records bound to the authenticated actor and exact assigned Agent, excludes tenant-wide memory/knowledge/graph stores, emits no private query trace, and disables sibling council delegation. Project and Workspace scope require exact canonical membership. Mission scope requires an attached owned Mission, resolves its compatibility ID to that exact canonical Project membership, and does not create a separate Mission memory store. Personal scope requires the exact authenticated owner's active, versioned standing-consent generation; it retrieves only canonical owner-private coordinate-free memory, emits no private query trace, disables tools, web search, sibling council delegation, and response consolidation, and must persist the shrink-only automatic compiler receipt before model disclosure. Workflow plan/start accepts Mission, Project, and Workspace scope with the corresponding coordinate, Agent-private scope with an exact `agentId`, and Personal scope with current owner consent. Planning stores only the relevant content-free authority digest. Start discards caller-supplied private bindings, creates a server-only envelope bound to the immutable workflow root, and public projections remove it. Durable retrieval, every later step, and every plan/replan revalidate current membership, Agent identity/grants, or the exact consent generation and fail if root authority, expiry, membership, identity, grants, consent, or the reviewed plan boundary changed. Agent-private and Personal database access always has null Workspace, Project, and Mission coordinates. A non-empty, query-matched `contextSelection` authorizes only that direct request to compile the authenticated canonical user's selected private-memory IDs in personal `all` mode. Context Compiler v2 intersects that legacy-selected set with independently authorized evidence and may only remove candidates; its metadata-only canary receipt must persist on the actor-bound run before the provider call. Receipt failure blocks disclosure. An explicit user-private selection exposes no tools and skips legacy prompt/response consolidation. Personal durable access exists only through its server-created root-bound envelope and current consent; no background worker receives a free-standing private prompt grant. The run's `harness` event reports `memoryFormation`: `durable` only when the run's effective memory mode is `all` and it carries no explicit-selection, shared, or Personal prompt access (an unscoped all-memory run or an Agent-private run), otherwise `withheld`. An approval resume keeps the original decision, so a withheld run never consolidates memory or saves an assistant inference candidate.
- `POST /api/agent` accepts `strategy` as `auto` (the default), `direct`, or `durable`. `direct` is a preference: a request that invokes a saved procedure still starts that procedure's workflow. Local Computer Use, `contextReferences`, and a `contextScope` that carries durable memory (`agent_private`, `mission`, `project`, `workspace`, `personal`, or `explicit_selection`) always run direct, and asking for `durable` with such a scope returns `409`. The `none`, `current_turn`, and `session` scopes may start a workflow, which retrieves no saved context. The web and native clients send `auto`.
- `POST /api/agent` accepts optional `requireReadOnlyAgent: true` for ledger replay. It requires `agentId` naming a custom Agent whose same resolved execution principal has `approvalPolicy: "read_only"`; the check precedes request admission. Constrained requests use `messages` and reject `message`, `threadId`, resumes, missions, Computer Use, and queued dispatches with `409`. They force direct execution even for saved procedures, refuse tasks requiring clarification, and use the existing read-only tool policy through the governed executor and continuations. Retrieval remains available, but explicit memory, assistant inference candidates, and consolidation are withheld. Ordinary run events and usage receipts still persist. The flag participates in the request fingerprint.
- Direct `POST /api/agent` requests are replay-safe when the client names them. Send a body `requestId` or an `Idempotency-Key` header (1–200 letters, numbers, dots, underscores, colons, or hyphens); sending both with different values returns `400`. The first request binds the ID, per tenant and actor, to a SHA-256 fingerprint of its validated body. The fingerprint leaves out the ID itself, and a `threadId` that names the thread this request created counts as no thread. The root run, a new thread, the user turn, and a durable workflow's acknowledgement turn take IDs derived from the request ID. A retry with the same ID and body never runs the work twice. A completed run streams `run`, a `Replayed` status, and `done` with the recorded response. A failed run streams `run` and its redacted `error`. A canceled run streams `run` and `canceled`, and is not run again. A run paused for approval or clarification streams its `waiting_approval` or `clarification` event. A request that became a durable workflow streams `delegated` with that workflow's recorded approval choice. A run that is still going is not started again: the retry streams that run from its event log, as `GET /api/runs/:id/stream` does, after the `Last-Event-ID` it sends, and ends on the run's stored outcome. If the earlier attempt stopped before it created its run or workflow, the retry runs under the same IDs. Reusing an ID for a different body returns `409` with `code: "request_id_reused"`. If the binding cannot be read or written, the request fails closed with `503` and `Retry-After: 30` before any work starts. A voice command's retry is still treated as voice, even though its first attempt consumed the realtime session. Replays count against the agent rate limit. Requests without a client ID get a random server ID and no replay protection. Resumes (`resumeRunId`) continue their own run, and prompt-queue dispatches are bound by the queue, so neither is bound as a new request. The Command workspace keeps an ID only while the same message is resent, and starts a new one after Stop, an aborted stream, or a cancellation.
- `GET /api/command/catalog` returns the authenticated actor's private/no-store, partially available catalog of selectable Agents, Skills, enabled Extensions, Projects, connected Integrations, and ready Library files; only ready files are selectable. A direct `POST /api/agent` may carry the resulting bounded `contextReferences`; the server ignores caller labels, re-resolves every ID and version/digest binding, enforces a single primary Agent and Project, and records only content-free pins. File revalidation resolves the exact Library authority and source ID under canonical/exact actor readability and fails closed on duplicate or mismatched projections. These references add guidance or source data but no tool, OAuth, filesystem, delegation, membership, or mutation authority. Ready Capture files may contribute verified bounded indexed evidence or verified text as untrusted model input after current-content and extraction-integrity checks. An actor-private connected source may contribute a bounded verified cognition excerpt only when its current source item, revision, document, purpose, retention, content hash, chunks, and evidence lineage agree. Shared, metadata-only, unlinked, binary, and integrity-ineligible sources do not inject a body. Changed references fail with `409`, missing references with `404`, and unavailable revalidation with `503`. Ephemeral references are direct-run only and are not accepted by workflow planning or the persistent prompt queue.
- `GET|POST /api/command/prompt-queue`, `PATCH|DELETE /api/command/prompt-queue/:id`, and `POST /api/command/prompt-queue/reorder` manage the authenticated actor's persistent Command queue. Create accepts one bounded prompt, mode, direct/auto strategy, exact Agent ID, stable client correlation ID, and strict Conversation/Mission/Project plus `asael|local_macos` target. The server seals prompt text, resolves and pins the exact Agent definition/principal and configured provider/model route, caps the active queue at 40, and returns `409` for stale revisions or correlation reuse with changed intent. Reorder must name the complete queued/paused set and is atomic. Queue operations never grant execution, context, tools, approvals, budgets, or Computer Use authority. Queue identity is deliberately split: the canonical authenticated `omni_auth_users.actor_id` owns storage, RLS, sealing, lifecycle, and dispatch admission, while the request actor remains only the compatibility coordinate for resolving existing Agent, Settings, and model-routing pins and reading the exact legacy-owned run during stale-lease reconciliation. Neither identity is accepted from the request body, and a session without a canonical account binding fails before queue mutation or dispatch.
- `POST /api/command/prompt-queue/:id/dispatch` accepts the exact lifecycle revision and optional explicit `force` for a paused item, then streams the ordinary governed `/api/agent` SSE response. Authentication runs before production-origin validation, origin validation runs before claim, and dispatch revalidates Agent/model pins before binding a short-lived one-time raw token to the current native/browser session. After admission leaves its database request scope, the route performs a separate canonical HTTPS request to `/api/agent`; it overwrites the queue ID/token and active release-revision headers, strips forwarding and hop-by-hop headers, refuses cross-origin redirects, requires a successful SSE response, and fails the claim closed when the active release differs. `/api/agent` independently re-derives the canonical owner, consumes the exact sealed prompt/mode/strategy/Agent/target admission once, and persists run-link and terminal receipts in its event loop before exposing those events. Terminal completion, failure, cancellation, approval/clarification wait, or durable delegation clears the dispatch token and lease. Disconnect or lease expiry never blindly replays work: a durable run ID reconciles to its canonical run state, while absence of a durable link records failure and requires an actor resume. Web and native clients consume the same states; the native encrypted offline outbox replays original correlations/revisions and reports conflicts instead of overwriting newer server state.

- Native v28 may send strict optional `modelSelection` on a fresh `/api/agent` request. It is unavailable for resume and durable execution; an explicit selection forces direct execution and disables team fan-out, while an explicit built-in or custom Agent remains authoritative. The server revalidates the exact assignment ID, revision, configuration SHA-256, scope, provider, model, lifecycle/capability readiness, connection, credential, and supported reasoning intensity. Selection evidence persists only a content-free `commandSelectionSha256` plus effective provider/model/reasoning receipt fields; prompt content and private reasoning are excluded. A conflicting durable explicit-selection request returns private/no-store `409` before model execution.

- `POST /api/agent` accepts optional `computerUseTarget: "local_macos" | "isolated_browser"` only as a transition-compatible request shape. Omission carries no local-control grant and no prompt text can infer **This Mac**. `local_macos` is accepted only from an authenticated compatible macOS client, starts an exact tenant/actor/correlation/run-bound session, selects the direct agent path, and exposes only the closed `local.macos.*` allowlist. The submitted natural-language objective authorizes only the same run's bounded navigation, selection, media-control, and non-sensitive text-entry steps; visual actions are serialized and consume the run's visual-action budget. Submit, transfer, destructive, financial, account/security, permission, unknown, broad modified-shortcut, and direct-command effects retain ordinary per-action approval. Post-action screenshot and Accessibility evidence is one-turn-only and never enters the durable continuation. `isolated_browser` is retired: new requests return `410 computer_use_target_retired`, saved continuations fail closed with a typed `execution_target_retired` run event, and neither path redirects to **This Mac**. The former browser profile, takeover, activity, frame, snapshot, and stream product routes return `410`; retained database rows are audit history, not API or execution authority. App Builder's separate legacy browser-evidence field remains readable as non-gating history.
- `POST /api/agent` accepts optional strict `voiceInput` on a fresh `message` request: `schemaVersion: 1`, `source: "realtime_voice"`, the realtime `sessionId` and `conversationId`, `provider: "openai"`, the content-free `confidenceBand` (`high`, `low`, `unavailable`, or `edited`) with optional `confidenceMean`/`confidenceMinimum` in [0, 1] and `confidenceSampleCount`, `reviewMethod: "send_button" | "explicit_checkbox"`, and `reviewAttested: true`. `threadId` must equal `voiceInput.conversationId`, and `resumeRunId` is invalid with it; the web client and native v30 send it. Neither the declaration nor its absence is trusted alone: an unmarked command is also voice while the same tenant and actor hold a realtime session on that conversation that started or reconnected within 30 minutes, was not canceled or failed, and has not been named by a later reviewed or inferred command. A voice command requires approval for every tool above risk zero, including actions This Mac task authority would cover, never takes the recent-runs canary or model-text shortcuts, and pauses a durable workflow it starts before consequential actions. The thread stream records `voice.command_reviewed` with `sessionEvidence: "minted" | "not_found"`, or `voice.command_inferred` with the session IDs and `inference: "pending_voice_session" | "voice_history_truncated"`; both carry a transcript digest and length, never the text. A failed session-history read returns private/no-store `503` with `Retry-After: 30`, and a resume keeps the policy its run started with.

  matches a Google domain should match the part before the colon.
- `GET|POST /api/capabilities/rollouts` exposes the tenant-bound capability rollout control plane. Authorized security readers may inspect a current generation by capability ID; trusted system automation may register or compare-and-swap a generation transition as a risk-3 operation. Responses expose opaque identifiers and hashes, never private capability payloads.

Connector API records never contain credential plaintext or sealed payloads. App-managed bearer credentials are decrypted only immediately before the exact-origin MCP request; deployer-managed connector records reference environment-variable names instead of values. Registration does not make an endpoint safe by itself; discovery/import and execution remain subject to network, role, risk, and approval policy.

- `GET /api/evaluations/failure-feedback` returns the authenticated tenant's bounded recurring-failure clusters, review-only harness proposals, and aggregate counts with `private, no-store` caching. `POST` accepts either an explicit `review` decision with durable reason evidence or a `replay` request. Review never applies a harness change. Replay queues only the exact current evaluation case while its stored definition digest still matches, runs through ordinary evaluation governance, and never inherits mutation authority; changed definitions return `409`, mutation-capable cases remain blocked without their normal explicit governance, and cross-tenant identifiers are hidden.
- `GET /api/evaluations/ledger-replay` exports a ledger-replay corpus as a private, no-store attachment, with `read` on agent runs. It samples the tenant's 200 most recent runs, retaining only the authenticated caller's canonical/current actor pair and readable parent threads before reading events or counting candidates. It keeps completed runs from the last `days` (1–30, default 7) in an order fixed by a hash of the tenant and run, up to `limit` tasks (1–50, default 20). A run is left out, and counted by reason, when it was a conversation, the owner marked it as needing work, its goal is empty, over 2,000 characters, or carries contact details, a link, a long number, an opaque token, a credential word, or redacted text, it needed an approval, was blocked, called a tool capable of writing (including a dry run), filled a whole event page, or made no model call. Each task's goal is the run's only user message. Its assertions require the run's tools, a citation when the run cited, half its answer length up to 80 characters, three times its latency (at least 30 seconds), and twice its cost when that cost was known. Run `EVAL_TASKS_FILE=<file> EVAL_AGENT_ID=<read-only-agent> npm run eval:agents` against a candidate deployment with `EVAL_EMAIL` and `EVAL_PASSWORD` supplied in the operator environment. The runner requires a custom Agent and sends `requireReadOnlyAgent: true` for server enforcement. Optional `EVAL_TENANT_ID` and `EVAL_ACTOR_ID` verify the signed-in identity before execution; `EVAL_MODEL_SELECTION` pins the candidate model. `BASE_URL` accepts an HTTP loopback development origin or the canonical Asael production/staged Vercel origins; replay belongs on a candidate. `SMOKE_INTERNAL_AUTH_SECRET`, when supplied, labels synthetic telemetry only, and `VERCEL_AUTOMATION_BYPASS_SECRET` supports protected staged deployments. The runner does not follow redirects or retry paid POSTs, and a failed logout fails the command. Scoring requires a successful terminal `done` event, and any unpriced model call leaves the total cost unknown. The export records `evaluation.ledger_replay_exported` with counts only.

## Common status codes

- `400`: body/schema validation failed.
- `401`: authentication is required or invalid.
- `403`: authenticated identity lacks the required action/role.
- `404`: resource is absent or intentionally hidden across tenant boundaries.
- `409`: state transition conflict, including a request ID reused for a different agent request (`request_id_reused`).
- `413`: request body exceeds the configured limit, or an uploaded document exceeds an extraction safety limit (`archive_too_large`, `extraction_resource_limit`).
- `429`: a shared Postgres-backed safety limit was reached (single-process fallback is used only outside durable deployments).
- `503`: production storage, cron, or a required dependency is unavailable.

## Configuration precedence and safety

Application configuration comes from process environment variables. `NEXT_PUBLIC_*` values are embedded into browser bundles at build time; everything else must remain server-only. Set the production `NEXT_PUBLIC_APP_URL` to exactly `https://asael.bennierichard.com`. Vercel supplies deployment metadata through `VERCEL_*`. The worker reads `OMNIAGENT_WORKER_BASE_URL`, then `NEXT_PUBLIC_APP_URL`, then `BASE_URL`.

Use `.env.example` for the full supported list and defaults. Production-required values and operational smoke credentials are separated there. Smoke-only `SMOKE_*` values belong in the CI secret store, not in the web deployment. See [deployment.md](deployment.md) for rollout and rotation guidance.
