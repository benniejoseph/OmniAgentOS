# API and Configuration Reference

All routes are under `/api`. The canonical production origin is
`https://asael.bennierichard.com`. JSON is the default request/response format;
`/api/agent` returns server-sent events. Dynamic IDs are opaque strings and
callers must not infer tenancy from them.

## Authentication

- Browser sessions use the `__Host-asael_session` cookie in production and `asael_session` locally. Login sets `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` in production.
- `GET /api/auth/session` is safe to call anonymously and reports whether auth is enabled and whether the request is authenticated.
- Internal automation sends `x-omni-internal-auth` with `OMNIAGENT_INTERNAL_AUTH_SECRET` plus explicit tenant, user, and role headers. Never accept those identity headers without the secret in production.
- Inbound MCP uses one-time-visible `asael_sk_...` service API keys created in Settings. Only a SHA-256 digest is stored. Existing `omni_sk_...` keys remain verifiable during the compatibility window. The verified key scope is intersected with the actor's enabled MCP export policy; neither layer can grant access by itself.
- Vercel cron uses `Authorization: Bearer <CRON_SECRET>` with `GET /api/workflows/tick`.
- The dedicated worker uses internal authentication with `POST /api/workflows/tick`.

Existing `OMNIAGENT_*`, `x-omni-*`, `x-omniagent-*`, and `omni_sk_...` names
remain stable wire and deployment compatibility contracts; they are not
product display names.

Viewer permissions cover protected reads. Operator permissions cover agent runs, workflows, evaluations, and routine tool actions. Admin permissions cover identity, connectors, security controls, and other high-risk configuration. Each route performs its own action-level authorization; a valid session alone does not guarantee access.

## Public and authentication routes

- `GET /api/health`: public liveness/readiness summary. Returns 200 for healthy or local degraded storage and 503 when a configured database is unhealthy.
- Public registration and access-request intake are disabled. `/signup` permanently redirects to `/login`.
- `GET|POST /api/onboarding/access-requests`: admin-only list and approve/decline workflow for historical requests in the Inbox.
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`.
- `POST /api/mobile/auth/login`, `POST /api/mobile/auth/refresh`, `POST /api/mobile/auth/logout`, and `GET /api/mobile/bootstrap` provide the native opaque-token contract. Current clients attest normalized platform/version/build/contract metadata; legacy clients remain accepted but compatibility-unknown. All responses are private and no-store.
- `GET /api/mobile/adoption` is admin/system (`read.identity`) only and returns tenant-aggregate, PostgreSQL-authoritative native compatibility evidence. It never returns per-device or per-session identifiers and always reports Agent catalog enrollment as held.
- `GET|POST /api/auth/control-plane`: admin-only tenant/user/membership administration. `POST` creates a workspace user and returns a generated initial password when one is not supplied.

## External A2A

- `GET /.well-known/agent-card.json` returns the minimal public Asael A2A Agent Card. `GET /api/a2a/extendedAgentCard` requires an active peer-bound service API key with `a2a:discover` and reveals only the local Agents allowed by that exact rollout.
- `GET|POST /api/a2a/peers` and `GET|PATCH /api/a2a/peers/:id` are authenticated owner-control APIs for reviewing, registering, listing, activating, pausing, and revoking exact peer generations. Registration performs SSRF-safe live discovery and pins HTTP+JSON `1.0`, the HTTPS interface, card and adapter digests, direction, credentials, allowlists, and hard limits. Outbound bearer material is sealed and never returned.
- `POST /api/a2a/message:send`, `POST /api/a2a/message:stream`, `GET /api/a2a/tasks`, and `GET|POST /api/a2a/tasks/:operation` implement the A2A 1.0 send, stream, list/get, subscribe, and cancel boundary. Requests require `A2A-Version: 1.0`, the A2A media type or JSON, a peer-bound service key with the exact discover/read/write scopes, trusted network/origin checks, and shared rate limits. Missing/older versions, redirects, URL/raw parts, mixed task coordinates, oversized content, inactive peers, and cross-owner references fail closed.
- `POST /api/a2a/delegated-tools/execute` accepts only the opaque task-scoped delegated Bearer token transported to an outbound peer. It requires the exact active rollout generation, unexpired token, working canonical task, live P8.7 safety lease, and allowlisted tool. Each distinct idempotency key atomically consumes one bounded append-only tool claim before invoking the normal governed executor with forced mutation approval; retries of that exact key are not charged twice. Responses are bounded redacted execution projections; raw delegated/provider credentials are never persisted or returned.

External messages, artifacts, and status remain untrusted observations. A remote `TASK_STATE_COMPLETED` maps only to canonical `completed_proposed`; only the existing exact parent verifier can record `result_accepted`.

Outbound dispatch rejects budgets above the fixed lower external authority,
repeated peers in canonical ancestry, exhausted depth/fan-out/root-task/root-cost
limits, and expired deadlines. The non-secret boundary is sent in message
metadata. Scheduled workflow maintenance closes stalled safety leases by
canceling the canonical task before its deadline or expiring it at the deadline.

## Agent, memory, and retrieval

- `POST /api/agent`: bounded message array and mode (`orchestrate`, `research`, `execute`, or `learn`); streams SSE events. Every new direct or Loop v2 run resolves its exact split Agent definition and security principal before execution and immutably binds their definition, persona, model-policy, prompt-contract, Skill, principal, and policy versions to the run. Recovery and clarification resume reload that existing pin instead of resolving current Agent state. The enrolled Loop v2 recent-runs canary may return a `clarification` event with `runId` and `threadId`, leaving that exact actor-owned run in `waiting_clarification` before any tool executes. An affirmative follow-up may include both IDs as `resumeRunId` and `threadId`; the server revalidates their actor/thread/agent binding and resumes under the original execution scope. A resume ID without its thread is invalid. Direct runs may send `contextScope` as `none`, `current_turn`, `session`, `agent_private`, or `explicit_selection`; only the last accepts `contextSelection`. Explicit selection must carry the exact query, ordered evidence IDs, and signed lock returned by `/api/retrieval/selection-lock`; stale, changed, cross-actor, or cross-tenant locks return `409`, and the raw lock is never persisted. Current-turn/no-extra-context requests discard supplied and stored history, while session keeps the actor-owned conversation but disables durable retrieval. Agent-private scope retrieves only records bound to the authenticated actor and exact assigned Agent, excludes tenant-wide memory/knowledge/graph stores, emits no private query trace, and disables sibling council delegation. Personal automatic, mission, project, and workspace scopes return `409` until their authority exists. A non-empty, query-matched `contextSelection` authorizes only that direct request to compile the authenticated canonical user's selected private-memory IDs in personal `all` mode. Context Compiler v2 intersects that legacy-selected set with independently authorized evidence and may only remove candidates; its metadata-only canary receipt must persist on the actor-bound run before the provider call. Receipt failure blocks disclosure. An explicit user-private selection exposes no tools and skips legacy prompt/response consolidation. Workflows and background workers do not receive request-only private prompt access.
- `GET|POST /api/agents` and `GET|PATCH|DELETE /api/agents/:id` manage the compatibility projection for custom Agents. PostgreSQL mutations atomically version behavioral definition fields separately from principal authority fields; custom Skill changes version each affected definition. `GET /api/agents/:id?mode=trash-preview` returns the exact expiring removal preview, and DELETE accepts only that preview before retiring the principal and moving the resource to Trash. Bare list GET remains exact-owner and marks its custom rows actionable; `GET /api/agents?ownerScope=readable` is the request-bound compatibility list used by Arsenal and the web Mission workspace. Detail GET and the compatibility list add `selectable` and `manageable`: exact-owner rows are actionable, while canonical compatibility rows are read-only and cannot enter Command, Mission assignment, or native mutation controls. Agent creation and updates return `409` when any selected custom Skill is unavailable to the Agent's exact persisted tenant/actor owner.
- `GET /api/agents/cards` returns the authenticated caller's five internal built-in `p8.5-agent-card:1` projections with private/no-store caching. Cards advertise exact definition identity, closed input/output schemas and their digests, semantic task kinds, modalities, tool policy, delegated-principal authentication requirements, protocol versions, and hard limits. They never include tenant/actor coordinates, execution principals, grants, endpoints, tokens, or credentials and do not enable external A2A. Supplying bounded `query` and `taskKind=general|coordinate|research|build|verify|memory` returns a deterministic, non-authoritative compatibility-ranked discovery receipt.
- `GET|POST /api/agents/:id/grants` lists or creates exact context and capability grants for one owned, manageable custom Agent; `DELETE /api/agents/:id/grants/:grantId` revokes one pinned grant. All responses are private/no-store and require canonical actor identity plus workflow-management authority. Create accepts a strict typed purpose, visibility, exact target/resource and operation IDs, bounded item/byte/invocation/cost/duration budgets, and an expiry from five minutes through one year. Every mutation rotates the Agent principal, reissues retained live grants to the new generation, revokes the prior generation and grants, pins the new exact grant IDs, and emits metadata-only held/activated/revoked events. Equivalent, stale, cross-owner, expired, wildcard, or unpinned requests fail closed. Built-in and readable compatibility Agents cannot be widened through these routes.
- `GET|POST /api/agents/:id/release` reads or transitions one exact-owner custom Agent release. `POST` accepts only `evaluate`, `promote`, `rollback`, or `retire`: evaluation names the candidate definition version; promotion and rollback name an immutable evaluation bound to the current active baseline; retirement requires the literal confirmation `RETIRE AGENT`. Responses are private/no-store and require canonical actor identity plus workflow-management authority. Draft updates never become executable implicitly, stale transitions return `409`, retirement is terminal, and built-in or readable compatibility Agents cannot use this route.
- `GET|POST /api/agents/:id/adaptations` reads or transitions the canonical actor's evidence-gated adaptations for the exact current Agent identity. GET returns the current `definitionVersion` and private lifecycle records. POST accepts only explicit `refresh`, `evaluate`, `activate`, or `rollback`; the latter three require the exact deterministic `adaptationId`. Refresh observes owner corrections without activating them, evaluation is bound to the observed/current release and versioned policy, activation requires a passed exact-release evaluation and assigns a monotonic version, and rollback is terminal. Only exact-owner active adaptations enter new prompts, and their effect is restricted to non-authority instruction guidance.
- Each Agent definition has one strict persona object containing charter, operating style, voice, visual identity, allowed domains, escalation behavior, and success measures. Older compatible create payloads receive the conservative default persona, while updates replace the full object. Persona content remains untrusted behavior and cannot grant authority.
- `GET|POST /api/skills` and `GET|PATCH|DELETE /api/skills/:id` manage the Skill catalog. `GET /api/skills/:id?mode=trash-preview` returns the exact expiring removal preview, and DELETE accepts only that preview before moving the custom Skill and its surviving assignment snapshot to Trash. Request reads add `selectable` and `manageable` capability flags: built-ins are selectable but not manageable, exact-owner custom Skills are both, and canonical compatibility rows are read-only and cannot be assigned.
- `/api/runs` and `/api/runs/:id`: actor-private run history, events, and replay/continuation state. PostgreSQL enforces the authenticated owner boundary across the run, its thread/turns, event streams, checkpoints, resume claims, identity pin, and fork lineage; sibling actors in the same tenant cannot inspect them. Run detail returns `contextReceipt` when the runner persisted `run.context.receipt`: a content-free comparison of previewed, included, excluded, actually-used, and selected-but-dropped evidence IDs plus manifest/context/budget digests. `GET /api/runs/:id/trajectory` returns trajectory v3 with bounded event receipts, `outcomeEvidence`, a non-activating `outcomeEvaluation`, checkpoint steps, structural verification, parent/child fork lineage, that receipt's bounded metadata, and `traceHierarchy`: a nine-stage outcome journey derived only from events matching the run owner's tenant, actor, and correlation ID. Trace identifiers are hashed and raw prompt/tool/private-reasoning content is excluded. `POST /api/runs/:id/fork` accepts an exact `checkpointId`, a 1–4,000 character correction, and an optional bounded `requestId`/matching `Idempotency-Key`; it creates and executes a new owner-bound trace from the verified event prefix. The source trace is immutable, and the fork starts with a fresh execution scope, a newly resolved exact Agent identity, no inherited continuation, and no inherited approval. `GET /api/runs/:id/activity/stream` is a private/no-store server-sent projection that pushes owner-scoped browser actions and observation metadata and labels the persisted run `live` or `replay`. Raw frames and redacted accessibility snapshots remain behind `GET /api/runs/:id/activity/frames/:frameId` and `GET /api/runs/:id/activity/snapshots/:snapshotId`; neither raw representation appears in the activity JSON or Agent tools.
- Run detail also returns `agentIdentity`: `ready` contains the exact historical, internal-only identity card reconstructed from the immutable run pin, `unbound` marks a legacy run, and `definition_unavailable` marks a pinned custom definition that cannot be resolved. The card excludes principal, grant, budget, endpoint, credential, tenant, and actor data and does not enable external A2A.
- `POST /api/media/speech` accepts 1–5,000 characters plus an optional selected `agentId`. Built-ins resolve from the central definition; custom Agents require the authenticated request-bound owner read. Runtime attribution binds the selected Agent ID and a digest of its persona voice text without persisting that text. The current Google provider stays a neutral synthesizer; persona voice remains behavioral style and is not parsed into authority or arbitrary provider parameters.
- `GET /api/threads/:id` returns the owner-scoped thread, its newest 40 raw turns, and bounded episode summaries with private no-store caching. `POST /api/threads/:id` accepts only `{ "action": "rebuild_summaries" }` under memory-write authority and deterministically rebuilds source-linked turn, episode, optional project, and lifetime projections. Public summary records omit actor and tenant coordinates while retaining source lineage, rebuildability, and the purpose/scope digest. `POST /api/agent` accepts an optional validated `projectId`; new threads may bind that exact owner-scoped project, and an existing thread cannot be rebound.
- `/api/memory`, `/api/memory/graph`, `/api/knowledge`, `/api/ingest`, and `/api/retrieval/plan`. Authenticated session/mobile Retrieval Plan requests merge independently queried legacy memory and the current canonical user's private-memory cohort. Query-bearing Retrieval Plan responses add a short-lived `preview` token bound to the authenticated tenant/actor, exact query, ordered candidates, and context-pack digest. `POST /api/retrieval/selection-lock` accepts that preview plus the reviewed evidence-ID subset and returns request-ready `{ query, evidenceIds, lockToken }` with a content-free inclusion/exclusion receipt. Memory, knowledge, governed-tool, and Retrieval Plan searches use the provider-neutral P4.4 adapter: the credential-free local multilingual space is the default, external embeddings require explicit permission, vector spaces never mix, and the learned reranker runs only after scoped candidate reads. Search responses or context profiles include content-free embedding and reranker receipts; they never return embedding values. Returned context packs also include the P4.5 `budget` receipt and the same receipt under `profile.contextBudget`: lineage groups, tier allocation, truncation, duplicate-token share, effective model/task limit, estimated formatted tokens, compliance, and a digest. Evidence results carry only a hashed lineage reference, allocation tier, retained token estimate, and truncation flag; raw lineage identifiers remain private. A returned pack's `profile.queryPlan` is the versioned P4.3 plan: bounded semantic, temporal, entity, relationship, and procedural domains and queries plus validation and optional content-free model receipt metadata. Model hints cannot carry authorization fields, the original query remains anchored, and provider/schema/receipt failure is reported as a deterministic fallback. Scoped requests persist a separate immutable actor-private trace containing only the private-memory evidence component; tenant compatibility traces never receive the scoped query or results. Trace list and statistics responses merge tenant-compatible traces with only the current actor's authorized private traces. User-private memory writes and corrections also update a separately namespaced actor-private graph. `GET /api/memory/graph` and Retrieval Plan graph search merge only the caller's authorized private graph results with the compatibility lane; unscoped and sibling-actor requests cannot observe them. `GET /api/memory/graph?view=temporal_relations` selects the canonical actor's typed relation ledger; optional `entityId`, `relationTypeId`, repeated or comma-separated `epistemicKind`, `validAt`, `recordedAt`, `history=true`, and `limit=1..200` filters answer current, as-of, and change-history queries. The response is private/no-store and excludes access bindings, actor coordinates, contract digests, endpoint digests, and evidence identifiers. `GET /api/memory/:id?view=deletion-preview` requires memory-write authority and returns the exact descendant, retrieval-trace, graph-projection, and pending-run impact plus a receipt-manifest digest. `DELETE /api/memory/:id` requires that digest in `X-Asael-Deletion-Preview`; if the impact changed after review, deletion fails with `409` and requires a fresh preview. A successful response includes the permanent deletion receipt and exact invalidated-run counts.
- `GET /api/memory/reconciliation` returns the caller's merged legacy-compatible and canonical private confirmation/contradiction reviews; `status=pending|resolved|all` and `limit=1..200` are supported. `PATCH /api/memory/reconciliation` accepts a strict `{ reviewId, decision }` body where `decision` is `confirm_candidate`, `keep_existing`, or contradiction-only `keep_both`. Replaying the same decision is idempotent; a different decision returns `409`. Responses are private and no-store and omit embeddings plus review owner/resolver identifiers.
- `GET /api/memory/maintenance` returns frozen lifecycle policy v1 and pending, resolved, or all promotion reviews. `POST /api/memory/maintenance` accepts only `{ "action": "run" }` and returns the deterministic deduplication, decay, archival, and promotion-review report for the caller's authorized lanes. `PATCH /api/memory/maintenance` resolves a promotion review as `promote` or `dismiss`; promotion preserves exact source-memory lineage. `PATCH /api/memory/:id/lifecycle` accepts one strict `pin`, `unpin`, `archive`, or `restore` action. Responses are private and no-store; archival is reversible, excludes the memory and its graph lineage from retrieval, and never substitutes for reviewed deletion.
- `GET /api/entities` returns only the authenticated canonical user's actor-private entity, alias, resolution, and merge-review projection with `private, no-store` caching; internal access bindings, actor coordinates, and contract digests are excluded. `POST /api/entities` accepts the strict `review_merge` action for two distinct candidates under the exact canonical user review scope. Decisions are `approved`, `rejected`, or `reversed`; a reversal must name the exact prior approval. Ambiguous or stale candidates fail closed with `409`.
- `GET|POST /api/capture` lists or ingests Capture assets. Collection rows add `contentAvailable`, `indexable`, and `manageable`; exact-owner rows are actionable and canonical compatibility rows may be downloaded when their persisted content descriptor is valid, but cannot be indexed, changed, or deleted.
- `GET|POST|DELETE /api/capture/assets/:id` reads metadata or content, queues indexing, and deletes an asset. Public metadata and `content=1` GETs may read the validated canonical/current-email pair; PostgreSQL content is returned only after its persisted byte count and SHA-256 are verified in the same database read. Canonical compatibility rows remain read-only, while indexing, deletion, status changes, and linked knowledge cleanup stay exact-owner operations.
- `GET|POST /api/capture/recordings` keeps bare GET and creation exact-owner. `GET /api/capture/recordings?ownerScope=readable` is the web recording-history compatibility catalog: it returns summary fields only, marks every verified row `metadataDetailAvailable`, marks exact rows `detailAvailable` and `manageable`, and acknowledges `requestReadContracts.captureRecordings=readable_v1`. `GET /api/capture/recordings/:id?ownerScope=readable` returns a strictly validated public recording/segment metadata snapshot and acknowledges `requestReadContracts.captureRecordingDetail=readable_v1`; canonical history remains read-only and reports transcript, audio, and mutation capabilities as unavailable. Bare detail GET returns the full exact-owner recording and acknowledges `exact_v1`. Audio bytes, transcripts, completion, indexing, updates, deletion, and all other segment routes remain exact-owner.
- `GET /api/library` returns the authenticated actor's unified workspace asset catalog across Capture files, recordings and transcripts, Project and Mission artifacts, and current immutable connected-source revisions. Optional `q`, `kind`, `project`, `limit=1..100`, and `offset=0..10000` parameters provide bounded database-side search and pagination. Every row carries an explicit owner/workspace/project/work-item scope, current version, citations, and internal source/work links; the projection never copies bytes or exposes provider locators, credentials, or unbounded metadata. `total` is a lower bound and `nextOffset` is present when another page may exist. Responses are private and no-store and use the same `app.library.list` application service as the governed Agent tool.
- `GET|POST /api/customer-accounts`, `GET|PATCH /api/customer-accounts/:id`, and `POST /api/customer-accounts/:id/facts` expose the provider-neutral P10.9 Account 360 domain through the same `app.customer_accounts.*` application services used by governed Agent tools. Reads require canonical Workspace membership and return private/no-store account projections. Create, revise, and fact-record mutations require `manage.workflow`, risk-two review metadata, a request idempotency key, account-owner Workspace write authority, and immutable typed events. Account revisions retain explicit read/manage/customer-success purpose sets; new accounts keep external CRM writes disabled, while the separate P10.11 configure tool can move an exact owner-controlled revision to `approval_required`. Fact revisions cover organization, contacts, stakeholders, products, opportunities, cases, usage, projects, interactions, health, risks, and renewal; every returned current fact includes the exact source revision and digest, provider reference when external, permission basis, observation/validity/staleness times, derived freshness, confidence, semantic owner, and unresolved conflict IDs. Competing sourced values remain visible, retractions remain in history, and no raw provider credential or Salesforce mutation authority enters the contract.
- `GET /api/customer-accounts/salesforce` returns private/no-store read-sync health, exact Workspace context, per-object cursor/lag/scope, webhook readiness, bounded reconciliation findings, guarded-write deployment state and hashed recent operation receipts, and the Workspace-bound OAuth authorize URL. `POST /api/customer-accounts/salesforce/sync` and `POST /api/customer-accounts/salesforce/reconcile` require `manage.connector`; the former resumes bounded backfill/delta work and the latter performs read-only exact-record comparison without provider writes. `POST /api/webhooks/salesforce` is not session-authenticated: it accepts only the strict CDC relay envelope under the five-minute raw-body HMAC contract documented in deployment, resolves the exact digested Salesforce organization, hydrates the complete reviewed record, deduplicates immutable observations, and returns `202` even when no connection matches. OAuth authorize/callback/disconnect reuse `/api/oauth/:provider/*`, require the canonical Workspace owner boundary, and never expose provider tokens.
- `GET /api/customer-accounts/:id/health` returns the active deterministic policy, current explainable score, and bounded immutable score history with private/no-store caching. `POST` requires `manage.workflow`, an idempotency key, account-owner Workspace write authority, and the exact current Account 360 revision number and digest. It stores a new immutable score revision plus current projection and returns every factor's weight, score, confidence, evidence state, exact fact/source revision hashes, freshness/conflict penalties, overall coverage, confidence, policy version, and input digest. Optional model suggestions require exact current fact citations, are always marked non-authoritative, and cannot affect factor or overall scores. Changed account evidence returns `409`; an identical evaluation key returns its original immutable result.
- `GET /api/customer-accounts/:id/workflows` returns the immutable eight-workflow `asael-csm-pack:1` plus bounded current runs for the Account 360 with private/no-store caching. `POST` requires `run.agent`, account-owner Workspace write authority, an idempotency key, the exact current account revision/digest, and one strict workflow-specific input object; it creates an actor-owned Project and deterministic dependency-aware WorkItems but no external effect. `PATCH` requires `manage.workflow` and appends a completed, blocked, or cancelled outcome against an exact run revision. Completed outcomes must cover every definition-required artifact/evidence key, and every artifact/evidence reference is verified against the exact workflow Project before the immutable receipt is stored. Reusing a key with changed input, changing account evidence during launch, stale run revisions, unavailable artifacts, or unsupported evidence claims return `409`. Governed tools `app.customer_accounts.workflows.list`, `.start`, and `.outcome.record` use these same application services.
- `GET /api/customer-accounts/portfolio` returns the bounded `p10.14-customer-success-intelligence:1` portfolio ordered by deterministic attention state. Each account row includes current health and evidence currency, open/critical risk counts, open/overdue commitments, exact related approval count, stale/conflicting fact counts, and one digest-bound next-best action with confidence, uncertainty, freshness, citations, and the immutable declarations `suggested: true` and `authoritative: false`. `GET /api/customer-accounts/:id/intelligence` adds the cited risk rows, Account-linked Meeting commitments, metadata-only exact related approvals, and a newest-first timeline across immutable account/fact, health, workflow, and commitment revisions. Both routes require canonical Workspace membership plus the account-read purpose, are private/no-store, create no event or effect, and use the same application services as Agent tools `app.customer_accounts.portfolio.show` and `.intelligence.show`. Approval rows require independent `manage.workflow` authority and never expose reviewed inputs.
- `GET /api/today/agenda` returns the private/no-store `p11.1-cohesive-today:1` projection for the authenticated actor. Optional `workspaceId`, `workLimit`, `approvalLimit`, `meetingLimit`, and `accountLimit` values are strictly bounded. The response contains the canonical personal snapshot, agenda, Meetings, confirmed commitments, customer attention, approvals, Agent identities, workflow and Project work, consumption, per-source freshness/unknown state, visible sections, counts, projection digest, and a content-free application-service receipt. The service owns its canonical/current-email database scope, creates no domain event or external effect, and is also registered as governed tool `app.today.agenda.show`. `PATCH /api/today/brief` persists the actor's selected Today sections with the existing brief and notification preferences.
- Governed tools `app.customer_accounts.salesforce.writes.configure` plus the typed Contact, Task, Note, Case, Opportunity, and Account create/update operations are the only P10.11 mutation surface. Every record operation requires `manage.connector`, an exact Account 360 and provider revision, account-owner activation, a persisted risk-two approval, idempotent provider identity, and a verified effect receipt. Note is update-only; creates are limited to Contact, Task, Case, and Opportunity. Failed or mismatched verification is terminal evidence, not success, and response-lost execution reconciles before any retry.

## Workflows and operations

- `GET /api/meetings/:id/commitments` returns immutable evidence-bound commitment proposals, their single confirmed or dismissed resolution, and only the current actor's eligible participant email policies. `POST` accepts an exact processed-media revision and cited action-item ID and creates a proposal with no task or communication effect. `PATCH` confirms or dismisses the exact proposal digest. Confirmation requires a current participant owner, treats any non-cited owner or due date as explicit user confirmation, idempotently creates one canonical Project WorkItem, optionally creates one unsent governed follow-up draft under an exact matching contact policy, and attaches the resulting IDs to a new immutable Meeting revision. Draft delivery is never part of this route. All responses are private and no-store.
- `GET|POST /api/missions` keeps bare GET and creation exact-owner. `GET /api/missions?ownerScope=readable` returns only validated public mission summaries from the request-bound canonical/current-email pair and acknowledges `requestReadContracts.missions=readable_v1`; bare GET acknowledges `exact_v1`. `GET /api/missions/:id?ownerScope=readable&view=summary` re-proves one deep-linked public summary outside that bounded collection and acknowledges `requestReadContracts.missionSummary=readable_v1`; an exact summary may then use the unchanged bare detail route, while a retained canonical summary remains read-only. Exact-owner summaries advertise detail, management, and Command handoff capabilities. Full Mission detail, events, cancellation/archive, task creation/update/comments/review, attempts, artifacts, and runtime execution remain exact-owner. `POST /api/missions/:id/tasks/:taskId/start` requires an assigned ready WorkItem and `manage.workflow`, resolves the exact Agent identity, binds canonical workspace/project/work-item coordinates, reserves one active attempt, and idempotently queues the governed workflow. Assigned-task `running`, `succeeded`, and `failed` states are executor-owned and cannot be written through the generic task PATCH route; Mission detail projects the latest governed execution binding onto the WorkItem.
- `/api/workflows`, `/api/workflows/:id`, `/api/workflows/plan`, and `/api/workflows/executions`. `GET /api/workflows/:id/trajectory` returns the same actor-scoped, correlation-driven `traceHierarchy` for the exact workflow owner; a sibling actor receives no trace.
- `POST /api/projects`, `PATCH /api/projects/:id`, `POST /api/projects/:id/tasks`, and `PATCH /api/projects/:id/tasks/:taskId` accept `Idempotency-Key` using 1–200 letters, numbers, dots, underscores, colons, or hyphens. When omitted, the server binds the mutation to the trusted request ID or a generated request correlation. Authenticated project and manual-task creation are exactly replayable with a supplied key; reusing that key for different content returns a conflict. These paths write their versioned, metadata-only domain event in the same Postgres transaction as the canonical row.
- Workflow run responses preserve the legacy `status` field for polling and mutation controls. Full and list projections also add a display-only `canonicalStatus` plus `outcome`; `outcome` is either a schema-validated, metadata-only outcome contract and terminal receipt or `null`. New plans expose `outcome.outcomeContractBindingState: "pre_execution"` because the exact contract and digest were stored before approval or execution; historical plans without it remain `posthoc`. A missing, malformed, posthoc, or weakly verified receipt never upgrades legacy `completed` beyond canonical `unverified`. The compact `?view=status` response intentionally returns `outcome: null` because it does not load the result record.
- The first P1.4 canary adds the full `effectReceipt` only to the tool record for live `memory.write` performed as a single-tool node in an approved workflow with explicit tenant and initiating-actor scope. ## Tools and connectors

- The native memory tool family includes `memory.search`, `memory.inspect`, `memory.write`, `memory.correct`, `memory.forget.preview`, `memory.lifecycle`, `memory.forget`, and `memory.export`. Inspection returns the current public scope and retrieval eligibility without embeddings or access bindings. Forget requires the exact 64-character preview-manifest digest and human approval; process-loss recovery reads the deletion receipt under the same authenticated private-memory scope. Export returns `/api/data/export` plus version, inclusion, exclusion, and exact-owner receipt metadata; it never copies archive content into the tool result. Shared-scope changes remain unavailable until P3.1 authority is active.
- `GET /api/oauth` keeps its legacy connection list exact-owner. `GET /api/oauth?ownerScope=readable` returns only validated public metadata from the request-bound canonical/current-email pair and acknowledges `requestReadContracts.oauthGrants=readable_v1`. Authorization, callback, token opening/refresh, sync, Photos, and disconnect routes remain exact-owner.

- `/api/settings/providers`, `/api/settings/models`, `/api/settings/assignments`, `/api/settings/api-keys`, and `/api/settings/mcp` manage redacted provider connections, lifecycle-aware model selection, service keys, and the actor-owned MCP export boundary. Credential plaintext is accepted only on create/rotation and is never returned after storage. `GET /api/settings/providers?ownerScope=readable`, `GET /api/settings/assignments?ownerScope=readable`, `GET /api/settings/mcp?ownerScope=readable`, and `GET /api/settings?ownerScope=readable` opt their public metadata into strictly bound canonical/current-email reads; bare GETs stay exact. Assignment rows include `manageable` plus render-safe model identifiers; canonical routes are configuration-only, occupy their scope as a read-only continuity record, and never seed editable provider, fallback, or consent state. ## Common status codes

- `400`: body/schema validation failed.
- `401`: authentication is required or invalid.
- `403`: authenticated identity lacks the required action/role.
- `404`: resource is absent or intentionally hidden across tenant boundaries.
- `409`: state transition conflict.
- `413`: request body exceeds the configured limit.
- `429`: a shared Postgres-backed safety limit was reached (single-process fallback is used only outside durable deployments).
- `503`: production storage, cron, or a required dependency is unavailable.

## Configuration precedence and safety

Application configuration comes from process environment variables. `NEXT_PUBLIC_*` values are embedded into browser bundles at build time; everything else must remain server-only. Set the production `NEXT_PUBLIC_APP_URL` to exactly `https://asael.bennierichard.com`. Vercel supplies deployment metadata through `VERCEL_*`. The worker reads `OMNIAGENT_WORKER_BASE_URL`, then `NEXT_PUBLIC_APP_URL`, then `BASE_URL`.

Use `.env.example` for the full supported list and defaults. Production-required values and operational smoke credentials are separated there. Smoke-only `SMOKE_*` values belong in the CI secret store, not in the web deployment. See [deployment.md](deployment.md) for rollout and rotation guidance.
