Tasks are grouped by visible, testable outcomes. Each task extends the existing feature's controller/service unless explicitly marked new. A large task should be split at a usable behavior boundary before execution; avoid completing a collection of empty components without a working screen.

## Sequence and checkpoints

| Phase | Outcome | Dependencies and release checkpoint |
|---|---|---|
| 0 | Reviewed system and proven ATLAS delivery | Establish baseline and renderer proof before final asset export; checkpoint A freezes visual/asset contracts |
| 1 | Shared web foundation | Depends on system decisions; checkpoint B demonstrates shell, themes, controls and recovery on representative screens |
| 2 | Complete companion experience | Depends on 1; ATLAS static fallback allows functional work before final clips. Checkpoint C is a usable Assistant/voice/decision experience over existing capabilities |
| 3 | Work, Memory, Capture and Results | Depends on 1 and shared components from 2; checkpoint D preserves all work/data workflows |
| 4 | Specialist, capability, admin and public pages | Family work can parallel Phase 3 after 1; checkpoint E requires the applicable Phase 2 and 3 migrations too, completing all 38 web routes and subviews |
| 5 | Native/mobile/macOS parity | Renderer proof starts in 0; family migration can parallel 2–4 after shared contracts stabilize. Checkpoint F completes native parity |
| 6 | Bounded ongoing responsibilities | Contract work may start after 2; requires Work/Activity surfaces and separate governance tests. Checkpoint G is the read-only pilot |
| 7 | Reviewed effects and channel expansion | Depends on successful pilot and explicit scope; checkpoint H demonstrates one bounded action and a selected channel, each independently releasable |

Phases 0–5 are the complete visual and everyday interaction program. Phase 6 is the major new ongoing-assistant behavior. Phase 7 is planned expansion, not a reason to hold the visual release. Every checkpoint uses the quality/rollback gates, not just a screenshot review.

## Workstream ownership and release definition

Use one owner for shared design tokens/navigation/contracts; separate owners can take page families, native adaptation, ATLAS production and responsibility backend work. No two workstreams should independently redesign the composer, decision card or canonical domain model. Backend changes remain independently reviewable from asset/style changes.

For each migrated family, attach before/after states, behavioral checks, accessibility findings and performance deltas to its review. Keep a route/subview checklist from PAGE_PLAN.md and record remaining exceptions explicitly. “Revamp complete” means all existing routes, native families, overlays and failure states meet the quality gates; new responsibility and expansion milestones have their own acceptance evidence.

Implementation starts after the operational follow-ups are complete. Release mechanics follow the repository's current CI, paired web/runner compatibility and production promotion/rollback procedures. Production promotion also depends on the owner-held production credentials/signing materials through that procedure; no direct deployment substitutes for the gate. Complete locally reviewable code, assets and validation before reporting that external dependency. No checkbox or release is complete merely because implementation is authorized.
